PIPELINE ARCHITECTURE
----------------------------------------------------------------------
Natural Language Question
  |
  v
[sql_generator.py] — Rule-Based Decomposition Engine
  Step 1: detect_tables()   — keyword scan to identify tables needed
  Step 2: detect_agg()      — detect COUNT/SUM/AVG/MAX/MIN
  Step 3: detect_group_by() — detect GROUP BY from "per X" patterns
  Step 4: detect_filter()   — detect WHERE conditions (country, status)
  Step 5: build_columns()   — construct SELECT columns with quoted names
  Step 6: build_sql()       — assemble final SQL with JOINs
  |

[validator.py] — SQL Safety Gate
  - Blocks: DELETE, DROP, UPDATE, INSERT, TRUNCATE, ALTER
  - Blocks: Multiple statements, SQL comments
  - Only passes SELECT queries
  |
  v
[executor.py] — Query Runner with Retry Logic
  Attempt 1: Run SQL against PostgreSQL
  If SUCCESS → return results
  If FAILURE → pass error to fix_sql()
  |
  v
[sql_generator.fix_sql()] — Auto-Correction Engine
  - Fixes wrong table names (regex match on schema)
  - Fixes column case issues (adds double quotes)
  - Fixes ambiguous columns (adds table alias prefix)
  - Regenerates from scratch on syntax errors
  |
  v
[executor.py] — Retry Attempt
  Attempt 2: Run fixed SQL
  Log result (success or final failure)
  |
  v
[main.py] — Benchmark Runner
  Collect all results → Save logs → Print summary

DESIGN DECISIONS
----------------------------------------------------------------------

1. RULE-BASED APPROACH (no LLM/API required)
   Chose rule-based over LLM-based because:
   - Works offline, no API key needed
   - Deterministic and reproducible results
   - Fast execution (no network latency)
   - Easy to debug and extend
   - Suitable for a fixed, well-known schema (classicmodels)

2. DOUBLE-QUOTED COLUMN NAMES
   PostgreSQL lowercases unquoted identifiers by default.
   Since classicmodels uses camelCase (customerNumber, productLine),
   all column names are wrapped in double quotes to preserve case.
   Example: COUNT(customerNumber) → COUNT("customerNumber")

3. TWO-STEP DECOMPOSITION
   Mirrors the Task 2 structured thinking approach:
   Question → {intent, tables, columns, filters, joins} → SQL
   This makes the pipeline explainable and debuggable.

4. SAFETY FIRST
   validator.py runs BEFORE every SQL execution.
   Even retry attempts are validated before running.
   Blocked queries never touch the database.

5. MAXIMUM 1 RETRY
   Prevents infinite loops.
   Error message is used to diagnose and fix the specific issue.
   If retry also fails, result is logged as final failure.

6. STRUCTURED JSON OUTPUT
   Every query result is a consistent dict with:
   question, sql, result, status, retry_needed, retry_success,
   error, row_count, timestamp
   Makes evaluation, logging, and reporting easy.

RETRY / SELF-CORRECTION MECHANISM - HOW IT WORKS
----------------------------------------------------------------------

Step 1: First SQL attempt is executed
Step 2: If execution fails, error message is captured
Step 3: fix_sql() analyzes the error:
  - "relation X does not exist"  → corrects table name using schema lookup
  - "column X does not exist"    → adds double quotes for case preservation
  - "column X is ambiguous"      → adds table alias prefix (e.g. c."column")
  - "syntax error"               → regenerates SQL completely from scratch
Step 4: Fixed SQL is validated again (safety check)
Step 5: Fixed SQL is executed (retry attempt)
Step 6: Result logged regardless of outcome
Step 7: Maximum 1 retry — no infinite loops
